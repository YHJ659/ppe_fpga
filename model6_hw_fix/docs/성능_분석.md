# 왜 1 fps 가 안 나오는가

측정일 2026-08-08 · KV260(XCK26) · YOLOv8n 640×640 · SW(0\~5) + HW(6) + SW(7\~22)

---

## 답부터

**CPU 때문입니다. 그리고 이건 최적화로 넘을 수 있는 벽이 아닙니다.**

이 보드의 PS 는 Cortex-A53 4코어 @ 1.333 GHz 입니다.
YOLOv8n 을 640×640 으로 한 번 돌리는 데 필요한 연산량은 약 **8.7 GFLOPs** 입니다.

```
A53 이론 최대 = 4코어 × 1.333 GHz × 4 FLOP/사이클 = 21.3 GFLOP/s
프레임당 물리적 하한 = 8.7 GFLOPs ÷ 21.3 GFLOP/s = 0.41 초
                                            → 최대 2.4 fps
```

이 **2.4 fps 는 커널이 100% 효율일 때의 상한**입니다. 실제 컨볼루션은 메모리 때문에
피크의 30\~55% 밖에 못 냅니다. 그래서 현실적인 범위는 0.75\~1.4초, 즉 **0.7\~1.3 fps** 입니다.

실측 1.265초(0.79 fps)는 정확히 그 안에 있습니다. 이상 동작이 아닙니다.

### 소프트웨어가 성능을 흘리고 있는 게 아니라는 증거

같은 보드에서 직접 재봤습니다.

| 측정 | 실측 | 피크 대비 |
|---|---|---|
| 행렬곱 512² | **21.86 GFLOP/s** | **103%** |
| 3×3 conv (64ch, 160²) | 11.73 GFLOP/s | 55% |
| 1×1 conv (128ch, 40²) | 6.83 GFLOP/s | 32% |
| YOLO 전체 실효 (8.7 GFLOPs ÷ 1.16 s) | 7.5 GFLOP/s | 35% |

행렬곱이 **이론 최대치에 붙어 있습니다.** PyTorch 가 이 CPU 를 제대로 쓰고 있다는 뜻입니다.
스레드도 4개 전부 쓰고 있고 mkldnn 도 켜져 있습니다. 튜닝으로 나올 여지가 없습니다.

## FPGA 를 붙였는데 왜 안 빨라졌나

**model.6 은 전체 연산의 6.5% 입니다.** 이게 핵심입니다.

암달의 법칙으로 상한이 정해집니다. 6.5% 를 **무한히 빠르게** 만들어도

```
최대 배속 = 1 / (1 - 0.065) = 1.07배   →   0.79 fps 가 0.85 fps 로
```

즉 model.6 을 아무리 잘 만들어도 **7% 이상은 원리적으로 불가능**합니다.

그리고 실제로는 7% 도 못 얻습니다. 데이터를 PS↔PL 로 왕복시켜야 하기 때문입니다.

```
소프트웨어로 하면        0.077 초
FPGA 로 하면 (왕복 포함) 0.055 초
------------------------------------
실제로 아낀 시간          0.022 초  =  전체의 1.7%
```

**한 블록만 FPGA 로 빼는 구조로는 속도가 오를 수 없습니다.**
전송·양자화 비용이 아낀 계산량과 비슷하기 때문입니다.
이번 작업의 값어치는 속도가 아니라 *하드웨어가 소프트웨어와 같은 답을 낸다*
는 것을 증명한 데 있습니다. 그건 검증 결과로 확인됐습니다.

## 그럼 어디까지 갈 수 있나

이관 범위별 상한입니다. **왕복 비용을 0으로 놓은, 도달 불가능한 낙관치**입니다.

| 이관 범위 | 남는 SW 비중 | 최대 배속 | 상한 fps |
|---|---|---|---|
| model.6 만 (현재) | 93.5% | 1.07배 | 0.85 |
| C2f 8개 전부 | 50.4% | 1.98배 | 1.57 |
| C2f 8개 + Detect | 23.9% | 4.18배 | 3.3 |
| 전 레이어 | 전처리+NMS 만 (0.071 s) | — | FPGA 처리시간에 좌우 |

C2f 8개를 다 옮겨도 **2 fps 를 못 넘습니다.** Detect 하나가 26.5% 를 차지하기 때문입니다.

### 그런데 여기 함정이 있습니다

위 표는 왕복 비용을 뺀 값입니다. 실제로는 **블록마다 따로 왕복하면 그 이득이 사라집니다.**

```
model.6 한 블록의 왕복 = 0.050 초 (입력 204,800 B + 출력 409,600 B)
블록마다 따로 왕복하면  = 8개 × 0.050 = 0.40 초
```

C2f 8개를 옮겨 아끼는 계산 시간이 0.59초인데, 왕복에 0.40초를 쓰면 남는 게 0.19초입니다.
1.98배가 1.18배로 줄어듭니다.

**결론: 블록을 따로따로 옮기면 안 됩니다.**
여러 블록을 PL 안에서 **연달아 스트림으로 연결하고, 중간 결과를 PS 로 내보내지 않아야**
합니다. 그래야 왕복이 프레임당 한 번으로 줄어듭니다.

다행히 C2f 8개는 구조가 전부 같습니다. 채널 수만 64 / 128 / 256 으로 다릅니다.
이미 만든 IP 를 채널 파라미터화해서 재사용할 수 있습니다.

## 그 밖에 해볼 수 있는 것

| 방법 | 예상 | 근거 |
|---|---|---|
| ONNX Runtime 으로 SW 교체 | 1.0\~1.5 fps | 커널이 더 좋고 레이어마다 Python 이 끼지 않음. 다만 위 물리적 상한 2.4 fps 는 못 넘음 |
| 입력 해상도 축소 | 큰 효과 | 단 HW 가 40×40 고정이라 640 이 강제됨. 바꾸려면 IP 재설계 |
| int8 양자화 (SW) | 제한적 | A53 은 dot-product 명령(ARMv8.2)이 없어 ARM 신형만큼 못 얻음 |
| 스레드 늘리기 | **0** | 이미 4코어 전부 사용 중 |

## 정리

1. **0.79 fps 는 버그가 아니라 A53 의 실력입니다.** 완벽한 구현이어도 2.4 fps 가 상한입니다.
2. **model.6 은 전체의 6.5% 라, FPGA 로 옮겨도 최대 7% 밖에 못 줄입니다.** 실제로는 1.7% 였습니다.
3. **속도를 원하면 여러 블록을 PL 안에서 연결해야 합니다.** 블록마다 왕복하면 이득이 사라집니다.
4. C2f 8개(49.6%) 를 연결해도 Detect(26.5%) 때문에 2 fps 를 못 넘습니다. 그 이상을 원하면 Detect 도 대상입니다.

## 부록 — 재현 방법

```bash
# 단계별 시간
python3 ppe_live.py --image test.jpg --repeat 3

# 레이어별 시간
python3 layers.py

# CPU 처리량
python3 bench.py
```

`layers.py` 는 ultralytics 의 `DetectionModel._forward_once` 와 같은 방식으로
레이어를 순회하며 각 레이어를 개별 계측합니다(4회 중 최소값 채택).
`bench.py` 는 512² 행렬곱과 3×3 / 1×1 컨볼루션의 실효 처리량을 측정합니다.

측정 중에는 카메라 스트림을 정지시켰습니다. CPU 를 나눠 쓰면 수치가 오염됩니다.

**한 가지 밝혀둘 것** — HW 구간 0.055초 안에서 FPGA 실제 연산 시간과 DMA·드라이버
오버헤드를 분리하지는 않았습니다. 12프레임 내내 0.050초로 일정했던 점은 하드웨어
쪽이 지배적임을 시사하지만, 확정하려면 별도 측정이 필요합니다.

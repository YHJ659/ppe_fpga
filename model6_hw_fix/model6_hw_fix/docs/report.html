model.6 FPGA 하드웨어 검증 — 원인·수정·결과

PPE 검출 YOLOv8n / KV260 (XCK26) · 구성 SW(model.0~5) + HW(model.6) + SW(cv2 + model.7~22) · 2026-08-08
결론. model.6이 FPGA에서 돌고, 소프트웨어 단독과 같은 검출을 낸다. 경계 텐서 y0/y1은 1600픽셀 204,800바이트 중 불일치 0. 보드 카메라로 실시간 동작(0.77 fps)까지 확인했다. 막고 있던 원인은 모두 규명되어 수정됐다.

1. 근본 원인

A파라미터 메모리의 주소 규약이 어긋나 있었다 (핵심). HLS가 INTERFACE bram 포트로 내보내는 주소는 바이트 주소인데, Block Memory Generator는 그것을 워드 주소로 읽는다. 원소가 float(4바이트)이므로 채널 c의 계수를 부르면 실제로는 4c번 칸이 읽히고, 주소선이 8비트라 256에서 되감긴다.

읽히는 칸 = (4 × c) mod 256   →   c = 0 일 때만 우연히 제자리
  • 영입력(모든 값 0)으로 규칙을 세우고 실제 이미지로 검증 — 128/128 채널, 100.00% 재현.
  • Vivado가 CRITICAL WARNING [BD 41-237] MASTER_TYPE ... (OTHER) vs (BRAM_CTRL)으로 내내 경고하고 있었다.
  • 8비트 가중치 BRAM은 바이트 주소 = 원소 번호라 무사했다. conv1x1의 곱셈·누적이 처음부터 정확했던 이유.
  • 깊이 2인 스케일 BRAM은 4·set mod 2 = 0이라 항상 슬롯0을 읽어 우연히 맞았다.
  • C 시뮬레이션은 배열 인덱스로 돌기 때문에 이 층이 존재하지 않는다. 그래서 여기까지 살아남았다.

BPS↔PL 버스 폭이 부팅 설정에 묶여 있었다. FPD_SLCR.AFI_FS (0xFD615000)는 FSBL이 부팅 때 psu_init으로 설정한다. PYNQ로 .bit만 바꾸면 적용되지 않아 PS는 32비트인 채로 남고, 이때 주소가 16으로 나눈 나머지 8인 레지스터 쓰기가 조용히 버려진다. DMA의 SA/LENGTH가 바로 거기라 전송 자체가 불가능했다. 또 AFIFM2 (0xFD380000)의 HP0 폭이 어긋나 DDR 쓰기가 16바이트마다 4바이트만 들어갔다.

CDMA 한 번에 보낼 수 있는 길이가 모자랐다. c_sg_length_width 기본값 14 → 16,383 B. 한 프레임 출력은 409,600 B다. HLS 스트림에 TLAST가 없어 나눠 받으면 첫 조각 직후 DMAIntErr로 멈춘다. 즉 나눠 받기는 원리상 불가능하고, 한 번에 받는 수밖에 없다.

Dbottleneck_router가 82픽셀에서 교착했다. 스트림을 소비하는 쪽이 생산이 끝난 뒤에 도는 순차 구조라, C 시뮬레이션에서는 hls::stream의 깊이가 무한이라 드러나지 않는다. DATAFLOW로 재작성했다.

E2프레임째부터 틀리는 문제가 숨어 있었다. bn_silu_128의 call_counter는 static인데 설계에서 cv2가 삭제되어 프레임당 1회만 불린다. 그래서 2프레임째에 슬롯1(cv2 값)을 읽는다. 단일 프레임 시험으로는 절대 잡히지 않는 종류다.

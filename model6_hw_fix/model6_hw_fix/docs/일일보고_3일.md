**[3] 오늘 진행 업무**
- 라우터 수정본을 포함해 비트스트림 재빌드, 보드 검증
- 하드웨어 출력과 소프트웨어 기준값의 수치 불일치 원인 규명 및 수정
- 파라미터 `.coe` 재배치 도구(`coe_stride4.py`) 작성, 빌드 스크립트 수정 후 재빌드
- DMA 전송 길이 폭 확장 후 재빌드, 전체 프레임 수신 확인
- 비트스트림 1회 로드 상태에서 12프레임 연속 구동 검증
- 검증 이미지 6장에 대해 소프트웨어/하드웨어 검출 결과 대조
- 보드에 PyTorch 환경 구성, 카메라 실시간 파이프라인(`ppe_live.py`) 구현 및 동작 확인
- 레이어별 소요 시간 및 CPU 처리량 실측
- 수정 내역 보고서 및 인수용 폴더 정리

**[4] 문제점 및 검토 필요 사항**
- 실시간 성능이 0.77 fps로 낮음. 실측 결과 model.6은 전체 연산의 6.5%이며, 전송·양자화 비용을 빼면 FPGA 이관으로 아끼는 시간은 전체의 약 1.7%에 불과. **한 블록만 이관하는 구조로는 속도 향상이 어려움**
- Cortex-A53 4코어의 이론 최대 21.3 GFLOP/s에 대해 행렬곱 실측 21.86 GFLOP/s로, CPU는 이미 한계. 소프트웨어 최적화 여지가 크지 않음
- y2/y3 구간은 float 기준과 대조한 것이라 y0/y1처럼 정확성을 증명한 것은 아님. 엄밀 검증에는 conv3x3·bn64·residual의 정수 모의계산기가 별도로 필요

**[5] 이전 문제점 해결 내용**
- **입력 82픽셀 정지** → `bottleneck_router`의 교착. 스트림을 소비하는 쪽이 생산 종료 후에 도는 순차 구조가 원인이며, C 시뮬레이션에서는 `hls::stream` 깊이가 무한이라 드러나지 않음. DATAFLOW로 재작성하여 **82 → 1600픽셀** 전량 통과
- **수치 불일치 (일치율 8%)** → 파라미터 BRAM의 주소 규약 불일치가 원인. HLS는 **바이트 주소**를 출력하는데 Block Memory Generator는 **워드 주소**로 해석. 원소가 float(4바이트)이므로 채널 c 조회 시 실제로는 4c번지가 읽히고, 주소선이 8비트라 256에서 되감김. 영입력 실험으로 규칙(`4c mod 256`)을 도출하고 실제 이미지로 교차 검증(128/128 채널 일치). 32비트 메모리 깊이를 4배로 확장하고 `.coe` 값을 4칸 간격으로 배치하여 해결. **일치율 8% → 100%, 불일치 0바이트 / 204,800**
- **출력 부분 수신(16KB)** → DMA `c_sg_length_width` 기본값 14로 1회 전송 한도가 16,383B. HLS 스트림에 TLAST가 없어 분할 수신 시 `DMAIntErr` 발생. 26으로 확장하여 409,600B 일괄 수신
- **경계 배열 순서** → 팀 테스트벤치(`tb_conv1x1_stream.cpp`)가 픽셀 우선(HWC)으로 규약을 확정하고 있음을 확인. 인수인계 문서의 CHW 기술은 오류이며, CHW로 해석 시 검출이 4건 → 2건으로 붕괴함을 실측
- **2프레임째 오작동(잠재)** → `bn_silu_128`의 `call_counter`가 static인데 설계상 cv2가 삭제되어 프레임당 1회만 호출되므로 2프레임째에 슬롯1(cv2 값)을 읽게 됨. 슬롯1을 cv1 값으로 덮어 해결. 12프레임 연속 시험에서 1바퀴째와 2바퀴째 결과가 비트 단위로 동일함을 확인
- **검증 절차 오류(자체)** → DMA 전송 한도를 레지스터에 시험 기록하여 알아내던 방식이, 그 기록 자체가 전송 개시 명령이라 주소 0의 데이터가 회로에 유입되고 있었음. 상수로 고정. 완료 판정도 Idle 대신 IOC 비트로 변경하여 프레임당 10.0초 → 0.05초

**[6] 잔여 미해결 문제점 내용**
- **BD 원본 부재.** `.xpr`/`.bd`/BD tcl이 버전 관리에 없어 현재 비트스트림은 `.hwh`에서 역으로 재구성한 스크립트 산물임. 원본 등록 필요
- **원본 BD의 동일 결함 여부 미확인.** BRAM 주소 규약 문제는 HLS bram 포트를 blk_mem_gen에 직접 연결하면 어느 설계에서나 발생. 원본 BD에도 존재하는지 확인 필요 (단서: 합성 로그의 `MASTER_TYPE ... BRAM_CTRL` 경고)
- **배포 방식.** PYNQ로 `.bit`만 교체하는 방식은 PS 설정을 적용하지 않아 매번 실행 시 레지스터 교정이 필요. XRT(`xmutil loadapp` + 디바이스트리 `xlnx,afi-fpga` 노드) 방식으로의 전환 검토 필요
- **URAM 여유 부족.** 60/64(93.8%) 사용 중. 추가 블록 이관 시 자원 제약이 먼저 걸릴 가능성
